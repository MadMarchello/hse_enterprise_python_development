## Блок 1. Сравнительный анализ архитектурных подходов

### 1.1. Критерии сравнения

Для данного масштаба релевантны не «чистота парадигмы», а четыре проверяемых свойства:

| Критерий | Почему он важен именно здесь |
| --- | --- |
| Тестируемость `calculate_hashes` | Задание явно требует чистой функции и эталонного assert |
| Изоляция SMTP | Сеть и секреты не должны попадать в юнит-тест хешей |
| Детерминизм отчёта | Хеш — функция байтов; нестабильный `repr` ломает воспроизводимость |
| Когнитивная нагрузка на сдаче | Преподаватель ожидает `python -m homework.main` и `pytest -q`, а не фреймворк |

Дополнительный ориентир — PEP 20 (*The Zen of Python*): «Simple is better than complex», «Sparse is better than dense». Это не запрет модульности, а запрет архитектуры, которую нельзя обосновать размером задачи.

### 1.2. Вариант A. Процедурный подход

**Суть.** Один модуль (`main.py` или `main.py` + экспорт функции хеширования в том же файле). Поток: данные → строка-отчёт → `bytes` → два дайджеста → SMTP. Состояние — локальные переменные.

**Плюсы**

- Минимальная поверхность для `python -m homework.main` (пакет `homework` уже задан src-layout’ом).
- Легко проследить причинно-следственную цепочку на демонстрации.
- Соответствует объёму «скрипт с тестом одной функции».

**Минусы**

- Смешение чистой логики и I/O (SMTP, `os.environ`) затрудняет юнит-тесты без monkeypatch всего модуля.
- Рост `main.py` повышает риск случайно захешировать разные срезы отчёта (ФИО vs полная строка).
- Сложнее соблюсти правило «хеши считаются от одного и того же UTF-8 представления»: нет явной границы «канонизация → encode → hash».

**Избыточность:** очень низкая. Риск — недостаточное разделение, а не лишние абстракции.

### 1.3. Вариант B. Модульный подход

**Суть.** Разделение по **ответственности** (SRP, не по «файлам ради файлов»):

| Модуль (концептуально) | Ответственность | Побочные эффекты |
| --- | --- | --- |
| представление типов / отчёт | сборка канонической строки | нет (желательно) |
| hashing | `str → (md5_hex, sha256_hex)` | нет |
| config | чтение настроек/секретов | чтение окружения |
| mailer | транспорт SMTP | сеть |
| `main` | композиция (orchestration) | вызов остальных |

Это не слоистая архитектура: модули находятся на одном уровне пакета `homework`, а зависимости направлены от `main` к чистым функциям и к адаптерам.

**Плюсы**

- Прямое соответствие пунктам задания (типы, хеш, почта, тест).
- `calculate_hashes` изолируется без классов.
- SMTP можно не импортировать в тестах хешей.
- История Git естественно ложится на этапы («structure → report/hash → mail/tests»).

**Минусы**

- При слишком мелком дроблении (один файл на 10 строк) навигация хуже, чем в одном модуле.
- Появляется необходимость явного публичного API пакета (`__init__.py` реэкспортирует или нет — решение студента).

**Избыточность:** низкая / умеренная. Для учебного «промышленного» минимума это стандартный компромисс.

### 1.4. Вариант C. Объектно-ориентированный подход

**Суть.** Сервисные классы (`ReportBuilder`, `HashService`, `SmtpMailer`) с инкапсуляцией конфигурации и, возможно, состояния (последний отчёт, кэш дайджестов).

**Плюсы**

- Удобная точка для Dependency Injection: конструктор принимает `Mailer`.
- Состояние SMTP-сессии (если когда-либо понадобится пул) естественно живёт в объекте.
- Близко к тому, как устроены промышленные SDK.

**Минусы**

- Для **чистой** функции `calculate_hashes(text: str) -> tuple[str, str]` класс не добавляет семантики: нет инварианта, который надо хранить.
- Лишние `__init__` на сдаче требуют объяснения, зачем объект, если нет состояния.
- Риск «анемичной модели»: классы как мешки со статическими методами.

**Избыточность:** средняя. Оправдан **один** объект/протокол на границе I/O (почта), а не OOP «сквозняком».

### 1.5. Вариант D. Слоистая / Hexagonal / Clean Architecture

**Суть.** Домен (отчёт, хеш) не знает об SMTP и `os.environ`. Инфраструктура реализует порты. Внешний мир входит через adapters. Классические источники: Alistair Cockburn, *Hexagonal Architecture*; Robert C. Martin, *Clean Architecture*. В Python это обычно выражают через `typing.Protocol` (PEP 544) или `abc.ABC` (PEP 3119).

**Плюсы**

- Максимальная тестируемость: домен тестируется без сети и без файлов.
- Явная граница «секрет не должен протечь в доменную модель».
- Хорошая демонстрация промышленного мышления — **если** преподаватель оценивает архитектуру, а не только результат.

**Минусы**

- Для одного сценария («собрать строку → хеш → одно письмо») появляются пакеты `domain/`, `application/`, `infrastructure/`, mapper’ы DTO — это **ceremony**.
- На устной защите легко потерять нить: «где живёт ФИО?»
- Противоречит YAGNI, если нет второго транспорта (файл, API) и второго способа хеширования.

**Избыточность:** высокая для данного ТЗ. Полезным является **один заимствованный приём** — порт для отправки письма — без полной слоистой иерархии.

### 1.6. Сводная таблица

| | A. Процедурный | B. Модульный | C. ООП-сервисы | D. Clean / Hexagonal |
| --- | --- | --- | --- | --- |
| **Суть** | Чистые функции и I/O в одном (или почти одном) модуле | Разбиение по ответственности | Классы инкапсулируют поведение и конфигурацию | Домен независим от инфраструктуры через порты |
| **Плюсы** | Прозрачность, мало файлов | Тестируемость без оверхеда | DI на границе I/O | Максимальная изоляция и заменяемость |
| **Минусы** | Смешение чистого кода и SMTP | Нужна дисциплина границ модулей | Лишние объекты без состояния | Избыточные слои и пакеты |
| **Тест хешей** | Возможен, если функция вынесена | Естественен | Естественен, но тяжелее | Естественен |
| **Тест почты без сети** | Только monkeypatch | Легко подменить функцию/объект | Легко | Идеален (порт) |
| **Избыточность для ТЗ** | Низкая (риск: слишком мало границ) | **Низкая–умеренная** | Умеренная | Высокая |
| **Соответствие src-layout** | Да | Да | Да | Да, но провоцирует глубокое дерево |

### 1.7. Исследовательский вывод блока 1

Для масштаба «один пакет `homework`, один вход `python -m homework.main`» рациональна **модульная процедурная композиция (B)** с **точечным портом** на SMTP (идея из D, без слоёв). ООП оправдан только если объект несёт ресурс (SMTP-соединение) или реализует протокол. Полная Clean Architecture здесь не выводится из требований: нет альтернативных адаптеров, нет сложного домена, нет жизненного цикла сущностей.

PEP 8 рекомендует группировать связанный код; он **не** требует классов. Индустриальный критерий: если модуль нельзя описать одним предложением ответственности — его стоит разрезать; если предложение одно — разрезать рано.

## Блок 2. Управление конфигурацией и секретами

### 2.1. Нормативная рамка

Задание запрещает хранить пароли, SMTP-токены и прочие credentials в исходном коде и в Git. Это совпадает с внешними нормами:

- **Twelve-Factor App, III. Config:** конфигурация, которая меняется между окружениями (включая credentials внешних сервисов), хранится в среде, а не в коде. Лакмусовая проба: репозиторий можно открыть, не компрометируя секреты.
- **OWASP Secrets Management Cheat Sheet:** типичная антипрактика — секреты в plaintext внутри исходников и конфигурационных файлов, попадающих в VCS. Цель — централизовать хранение, ограничить доступ, не логировать секреты.
- **CWE-798 (Use of Hard-coded Credentials)** — класс дефекта, который industrially сканируют secret-scanners (gitleaks, GitHub secret scanning).

Важно: переменные окружения — **не идеальное** хранилище (они наследуются дочерними процессами, видны в `/proc/<pid>/environ` на Linux, могут попасть в дампы). OWASP прямо отмечает этот риск для контейнеров. Для учебной однопользовательской машины env vars всё же являются **минимально приемлемым** каналом, если секрет не попадает в Git.

### 2.2. Сравнение механизмов передачи SMTP-учётных данных

| Механизм | Как попадает в процесс | Зависимости | Плюсы | Минусы | Пригодность для данной домашки |
| --- | --- | --- | --- | --- | --- |
| **Явные переменные окружения** (`os.environ` / `os.getenv`) | `export SMTP_PASSWORD=...` в shell, настройки IDE, CI secrets | stdlib (`os`) | Стандарт языка; 12-factor; низкий шанс закоммитить; нет лишних пакетов | Нужно помнить экспорт; секрет виден процессу; нет удобного локального файла | **Высокая** как канонический канал |
| **Файл `.env` + python-dotenv** | Библиотека читает `KEY=value` и **дописывает** в `os.environ` | пакет `python-dotenv` | Удобство локальной разработки; библиотека декларирует совместимость с 12-factor; `override=False` по умолчанию не затирает уже заданные env | Файл легко закоммитить; это *не* production secret store; появляется зависимость в `requirements.txt` | **Высокая** как DX поверх env, если `.env` в `.gitignore` |
| **Только `.env` без загрузки в environ** | ручной `open()` | нет | Кажется проще | Самодельный парсер хуже dotenv; всё равно файл на диске | Низкая: inventing a parser |
| **OS keyring** (macOS Keychain, Windows Credential Locker, Secret Service) | `keyring.get_password(service, username)` | пакет `keyring` + GUI/агент ОС | Секрет не лежит в дереве проекта; шифрование хранилища ОС | Плохо для headless/CI; сложнее воспроизвести на сдаче на другой машине; лишняя зависимость | Средняя: хорошо как *дополнительный* канал, рискованно как единственный |
| **Интерактивный ввод** (`getpass.getpass`) | tty | stdlib | Не хранится на диске | Нельзя автоматизировать; на сдаче неудобно; пароль всё равно попадает в RAM | Низкая как основной способ |
| **CLI-аргументы** | argv | stdlib | — | Пароль виден в `ps`; попадает в shell-history | **Неприемлемо** |
| **Облачные vaults** (AWS SM, Vault, 1Password CLI) | API / sidecar | инфраструктура | Индустриальный эталон OWASP | Полностью избыточно для учебного SMTP | Нецелесообразно |

**Архитектурный принцип:** приложение должно читать **уже существующий** `os.environ` (единый порт конфигурации). `.env` и keyring — *поставщики* значений в этот порт, а не конкурирующие API, размазанные по `mailer`.

python-dotenv официально: `load_dotenv()` ищет `.env`, парсит пары и добавляет их в `os.environ`, **не переопределяя** уже установленные переменные (`override=False`). Это позволяет на сдаче задать env вручную и не зависеть от файла.

`os.environ` в документации CPython — mapping, отражающий окружение процесса; изменение его влияет на `getenv` подпроцесса, если не указано иное.

### 2.3. Что именно конфигурировать (не секреты vs секреты)

Разделение 12-factor: «код не меняется между окружениями, меняется config».

| Категория | Примеры | Можно ли в Git |
| --- | --- | --- |
| Несекретная конфигурация | SMTP host/port (часто публичные), имя переменных | Да, как значения по умолчанию или `.env.example` |
| Секреты | пароль, app password, API token | Нет |
| Идентичность письма | ФИО, from/to | ФИО — в коде или env (не секрет); адреса почты — скорее config |
| Политика TLS | порт 465 implicit TLS vs 587 STARTTLS | Да (это не секрет) |

Провайдеры (Gmail, Yandex, Mail.ru, университетский SMTP) требуют **разных** host/port/режимов TLS. Жёстко прошивать пароль нельзя; жёстко прошивать host — допустимо, но снижает переносимость. Архитектурно лучше вынести host/port/user/password/from/to в один settings-объект.

### 2.4. `.gitignore` как контрольный барьер (не как единственная защита)

`.gitignore` **не шифрует** секреты и **не удаляет** уже закоммиченные файлы. Он лишь предотвращает `git add` неотслеживаемых путей.

Минимально обоснованный набор для данного проекта:

| Шаблон | Зачем |
| --- | --- |
| `.venv/` | виртуальное окружение; требование задания + непереносимые абсолютные пути |
| `.env` | локальные секреты dotenv |
| `.env.*` с исключением `!.env.example` | защита вариантов `.env.local`, `.env.production` |
| `*.pem`, `*.key`, `credentials.json`, `secrets.json` | типичные имена ключевых файлов |
| `__pycache__/`, `*.py[cod]`, `.pytest_cache/`, `*.egg-info/`, `dist/`, `build/` | артефакты, не относящиеся к секретам, но засоряющие историю |

Рекомендуемая дисциплина (проверяемо):

1. Сначала правила ignore, потом любые файлы с секретами.
2. В Git держать **только** `.env.example` с пустыми или фиктивными значениями (`SMTP_PASSWORD=`).
3. Проверка: `git check-ignore -v .env` должен показать правило.
4. Если секрет уже попал в историю — `.gitignore` недостаточен: файл остаётся в прошлых commit’ах; секрет нужно **ротировать** (сменить пароль приложения), а не считать «исправленным».
5. Права на локальный `.env`: по возможности `chmod 600` (практика, совместимая с OWASP-рекомендациями для файлов секретов).

Текущий корневой `.gitignore` проекта уже содержит `.venv/` и `.env` — это правильное направление; расширение шаблонов — решение студента после проверки, что `.env.example` не игнорируется.

### 2.5. Архитектура модуля конфигурации (только сигнатуры)

Цель интерфейса: **fail fast**, если обязательный секрет отсутствует; не возвращать частично пустой объект в SMTP-слой; не логировать password.

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class SmtpSettings:
    host: str
    port: int
    username: str
    password: str
    sender: str
    recipient: str
    use_starttls: bool


def load_smtp_settings() -> SmtpSettings:
    """Читает настройки из окружения процесса.

    Контракт: при отсутствии обязательных переменных — исключение,
    а не письмо с пустым паролем.
    """
    ...
```

Инварианты для самостоятельной реализации (без кода):

- `frozen=True` фиксирует, что settings — значение, а не мутабельный глобальный state (PEP 557 / `dataclasses`).
- Пароль присутствует в объекте только на время отправки; не сериализовать `SmtpSettings` в лог и не включать в отчёт, который хешируется.
- Имена переменных (`SMTP_HOST`, `SMTP_PASSWORD`, …) документируются в README и `.env.example`, а не «угадываются».
- Опциональный `load_dotenv()` вызывается **один раз** на границе приложения (`main`), а не внутри `calculate_hashes`.

Альтернативный порт (если выбран keyring):

```python
class SecretStore(Protocol):
    def get_smtp_password(self, username: str) -> str: ...
```

Тогда `load_smtp_settings` зависит от `SecretStore`, а не от конкретной ОС. Для домашки это уже вариант C/D; оправдан, только если студент сознательно демонстрирует заменяемость хранилища.

## Блок 3. Детерминизм и работа с типами данных

Это критический блок: **хеш-функция детерминирована, сериализация объектов — нет**. Расхождение хешей между запусками почти всегда означает, что в дайджест попали разные байты, а не «сломался MD5».

### 3.1. Почему `set` (и иногда `dict`) дают нестабильную строку

#### Механизм hash randomization

Документация языковой модели CPython (`object.__hash__`) фиксирует:

- значения `__hash__()` для `str` и `bytes` по умолчанию **солены** непредсказуемым значением;
- внутри одного процесса они постоянны, между запусками — нет;
- цель — защита от Hash-DoS (сложность вставки в dict \(O(n^2)\); advisory OCERT-2011-003);
- **изменение хешей меняет порядок итерации множеств**;
- Python **никогда не гарантировал** порядок элементов `set` (он также зависит от разрядности сборки);
- с 3.3 hash randomization включён по умолчанию.

Переменная `PYTHONHASHSEED` (документация cmdline):

| Значение | Эффект |
| --- | --- |
| не задана или `random` | случайное зерно на процесс |
| целое `[0, 4294967295]` | фиксированное зерно (воспроизводимый `hash()`) |
| `0` | **отключает** рандомизацию |

Фиксированный seed предназначен для self-test интерпретатора и кластеров, которым нужно разделять hash values — не как архитектурный способ сериализовать пользовательские данные.

#### Следствие для `repr(set)` / `str(set)`

`set` — неупорядоченная коллекция (tutorial, §5.4). `repr` обходит элементы в порядке внутренней таблицы, который зависит от хешей. Для множества строк это напрямую связано с `PYTHONHASHSEED`. Трекер CPython (bpo-37596) даже использует расхождение `repr(set)` при seed 0 и 1 как тест на недетерминизм.

Следствие для задания: если отчёт, который затем хешируется, содержит `str(my_set)` или `repr(my_set)`, **MD5/SHA-256 могут различаться между запусками**, хотя логика «правильная». Это выглядит как «баг хеширования», но это баг **канонизации**.

#### Словарь: другая история, тот же класс ошибок

С Python 3.7 сохранение **порядка вставки** — часть спецификации языка (*What’s New In Python 3.7*; datamodel: replacing key не меняет позицию, delete+insert — перемещает в конец). PEP 468 касается порядка `**kwargs`, но опирается на тот же ordered dict.

Поэтому:

- литерал `{"a": 1, "b": 2}` даёт стабильный `repr` между запусками **на 3.7+**, если ключи вставлялись в одном порядке;
- `dict` **не** «отсортирован по ключу»;
- если ключи/значения получены из `set` или из неитерационно-стабильного источника, `repr(dict)` снова плавает;
- вложенный `set` как значение словаря снова нестабилен.

`list` и `tuple` упорядочены по определению: их `repr` стабилен при стабильном содержимом. `bool`, `int`, `float`, `str` атомарны (оговорка: `float` NaN/`repr` и локаль на `float` обычно не мешают; для отчёта лучше фиксировать формат явно, если используете форматирование).

### 3.2. Архитектурные стратегии стабилизации отчёта

Ранжирование по качеству (лучше → хуже):

| Стратегия | Идея | Оценка |
| --- | --- | --- |
| **1. Каноническая сериализация** | Для неупорядоченных коллекций в **хешируемую** строку попадает не сырой `repr`, а явно упорядоченное представление (например, отсортированные элементы `set`, если они сравнимы) | Предпочтительно: детерминизм в коде, не в окружении |
| **2. Разделение display vs digest** | На экран — «как есть» (даже нестабильный `repr`); в хеш — отдельно собранная каноническая строка + ФИО | Честно, но нужно строго не смешать два канала (задание требует хеш **итогового** отчёта) |
| **3. Исключить нестабильные типы из хешируемого текста** | В отчёт входят типы, но `set` печатается через `sorted(...)` | Практически совпадает с (1) |
| **4. `PYTHONHASHSEED=0`** | Стабилизировать процесс целиком | Обходной путь: отключает защиту Hash-DoS; легко забыть на сдаче; не работает, если преподаватель запустит без этой переменной |
| **5. Надеяться, что маленький set «случайно» стабилен** | — | Академически неприемлемо |

Архитектурный вывод: **детерминизм — свойство функции построения отчёта**, а не свойство `hashlib`. Граница модуля «report»: на вход — значения типов, на выход — **одна** строка с документированной канонизацией. Функция хеширования не должна знать про `set`.

Дополнительно для ФИО и кириллицы:

- нормализация Unicode (NFC/NFD, модуль `unicodedata`) влияет на байты; для ФИО из BMP обычно достаточно одной формы, но смешение клавиатурных комбайнинг-символов даст другой хеш;
- перевод строки `\n` vs `\r\n` меняет байты; канон следует зафиксировать (обычно `\n` внутри Python-строки).

### 3.3. Байты, `str.encode` и тождество входа двух хешей

#### Что потребляет `hashlib`

Официальная документация: конструкторы (`md5`, `sha256`, …) питаются **bytes-like** объектами (`bytes`, `bytearray`, `memoryview`), не `str`. Метод `update` конкатенативен: `update(a); update(b)` ≡ `update(a+b)`.

MD5 описан в RFC 1321; SHA-256 — в FIPS 180-4. Оба — функции \(\{0,1\}^* \to \{0,1\}^{n}\). Разные байты ⇒ разные дайджесты. Одинаковые байты ⇒ одинаковые дайджесты **независимо от того, что эти байты «значат» как текст**.

MD5 криптографически сломан (коллизии; предупреждение в docs hashlib). В задании он используется как **контрольная сумма**, не как защита пароля. С Python 3.9 у конструкторов есть `usedforsecurity=True` по умолчанию; для не-криптографического checksum документация допускает `usedforsecurity=False` (актуально на FIPS-сборках, где MD5 может быть блокирован). Это не «ослабляет» алгоритм на обычном CPython, а маркирует намерение.

#### Способы получить байты из `str`

| Способ | Статус | Отличие |
| --- | --- | --- |
| `s.encode('utf-8')` | канон документации `str.encode` | явная кодировка; `errors='strict'` по умолчанию |
| `s.encode()` | то же при дефолте | с 3.x default encoding для `str.encode` — `'utf-8'` |
| `bytes(s, 'utf-8')` | эквивалент для `str` | другой конструктор, тот же кодек |
| `codecs.encode(s, 'utf-8')` | эквивалент | лишний импорт |
| `s.encode('utf-8-sig')` | **другой** результат | префикс BOM `EF BB BF` |
| `s.encode('utf-16')` / `'utf-32'` | **другой** | BOM и ширина кода |
| `s.encode('latin-1')` | не подходит для кириллицы | либо ошибка, либо не те байты |
| `errors='ignore'` / `'replace'` | **запрещён для хеша** | молчаливая потеря данных |

Почему задание настаивает на **одном** UTF-8 представлении:

1. Хеш считается от байтов, не от «текста». Два вызова `encode` с разными кодировками дают разные входы.
2. Даже два вызова с одной кодировкой безопасны только если строка **та же**. Если один хеш взять от ФИО, а другой от полного отчёта — это уже **разные сообщения**, что прямо запрещено ТЗ.
3. Привязка к одной переменной `payload: bytes` делает инвариант проверяемым: оба конструктора получают **тот же объект** (или равную копию тех же октетов). Это защита от регрессии «поправил отчёт для print, забыл для второго хеша».

Практический контракт функции (сигнатура задана ТЗ):

```python
def calculate_hashes(text: str) -> tuple[str, str]:
    """Вернуть (md5_hex, sha256_hex) от text.encode('utf-8').

    Оба алгоритма питаются одной и той же последовательностью байтов.
    """
    ...
```

Инварианты для самостоятельной проверки:

- внутри функции encode выполняется **один** раз;
- возвращаемые строки — `hexdigest()` (документация: удвоенная длина, только hex-цифры; удобно для письма);
- функция **чистая**: нет SMTP, нет чтения env, нет `print`.

## Блок 4. Паттерны интеграции с SMTP

### 4.1. Разделение «письмо как данные» и «отправка как I/O»

Стандартная библиотека уже проводит эту границу:

| Модуль | Ответственность | Сеть |
| --- | --- | --- |
| `email.message.EmailMessage` | RFC-ориентированная модель письма (заголовки, тело) | нет |
| `email` package в целом | **явно не предназначен** для отправки (docs: not designed to send via SMTP) | нет |
| `smtplib.SMTP` / `SMTP_SSL` | клиент SMTP/ESMTP (RFC 821, RFC 1869) | да |
| `smtplib.SMTP.send_message` | сериализация `email.message` и вызов `sendmail` | да |

Это готовый hexagonal-срез без фреймворка:

- **application/domain:** собрать текст тела (ФИО, MD5, SHA-256) в структуру письма;
- **infrastructure:** установить TLS, `login`, `send_message`.

Рекомендуемая оркестрация (концептуально):

```
load settings → build report string → calculate_hashes(report)
        → build EmailMessage(body)
        → mailer.send(message)
```

Ошибки, которых следует избегать архитектурно:

- конкатенация сырого SMTP-протокола вручную (`MAIL FROM` в строках) — дублирует `smtplib`;
- HTML-письма и вложения — вне ТЗ;
- логирование `SmtpSettings.password`;
- смешивание построения тела письма с `hashlib` (письмо содержит хеши, но не участвует в их вычислении).

TLS: для порта 465 документация указывает `SMTP_SSL` (implicit TLS). Для 587 типичен `SMTP` + `starttls()`. Выбор — свойство провайдера, его нужно читать из настроек, а не зашивать «как в туториале Gmail», если используется другой сервер. `ssl.create_default_context()` — индустриальный минимум проверки сертификатов (см. Security considerations в docs `ssl` / `smtplib`).

### 4.2. Порт для подмены SMTP в тестах

PEP 544 (`typing.Protocol`) задаёт **структурную** подтипизацию: реализация не обязана наследовать протокол, достаточно совпадения методов. `abc.ABC` (PEP 3119) задаёт **номинальную** иерархию и запрещает инстанцировать класс с нереализованными `@abstractmethod`.

Для одного метода отправки Protocol предпочтителен: Fake не должен наследовать инфраструктурный SMTP-класс.

```python
from typing import Protocol
from email.message import EmailMessage


class Mailer(Protocol):
    def send(self, message: EmailMessage) -> None:
        ...


class SmtpMailer:
    def __init__(self, settings: SmtpSettings) -> None:
        ...

    def send(self, message: EmailMessage) -> None:
        ...


class RecordingMailer:
    """Тестовая заглушка: сохраняет письма в памяти, сеть не трогает."""

    sent: list[EmailMessage]

    def send(self, message: EmailMessage) -> None:
        ...


def build_result_message(*, full_name: str, md5_hex: str, sha256_hex: str) -> EmailMessage:
    ...


def run(mailer: Mailer) -> None:
    """Точка композиции. Не создаёт SMTP внутри доменной логики."""
    ...
```

Смысл: `run` зависит от **порта** `Mailer`. На демонстрации в `main` передаётся `SmtpMailer`; в тесте оркестрации — `RecordingMailer`. Юнит-тест `calculate_hashes` **вообще не видит** `Mailer`.

Альтернатива ABC:

```python
from abc import ABC, abstractmethod

class Mailer(ABC):
    @abstractmethod
    def send(self, message: EmailMessage) -> None:
        ...
```

Выбор Protocol vs ABC не влияет на SMTP; влияет на то, обязаны ли заглушки явно наследовать базу. Для учебного проекта достаточно Protocol.

### 4.3. Зависимости: stdlib vs `requirements.txt`

Для SMTP и письма **не нужны** сторонние пакеты (`yagmail`, `emails`, `sendgrid`). Они скрывают учебную цель и добавляют supply-chain поверхность.

Минимальный состав (концептуально):

| Пакет | Куда | Обоснование |
| --- | --- | --- |
| `smtplib`, `email.message`, `ssl`, `os`, `hashlib`, `dataclasses` | stdlib | ТЗ покрывается без PyPI |
| `pytest` | `requirements.txt` и/или `[project.optional-dependencies]` | требование ТЗ |
| `python-dotenv` | только если выбран файл `.env` | DX, не функциональная необходимость |
| `keyring` | только если выбран OS store | иначе не тащить |

Дублирование `pyproject.toml` `[project] dependencies` и `requirements.txt` — известный drift-риск. Учебное ТЗ требует оба файла; инженерная практика: `requirements.txt` либо отражает runtime+test, либо генерируется из одного источника. Расхождение версий pytest между файлами — дефект воспроизводимости.

## Блок 5. Стратегия тестирования и верификации

### 5.1. Юнит vs интеграция в этом проекте

Классическое различие (IEEE / ISTQB, адаптировано):

| | Юнит-тест | Интеграционный тест |
| --- | --- | --- |
| **Объект** | Одна функция/модуль с контролируемым входом | Несколько реальных компонентов (файлы, сеть, ОС) |
| **Внешний мир** | изолирован | частично или полностью реален |
| **Скорость / детерминизм** | высокие | ниже; флейки (сеть, квоты SMTP, 2FA) |
| **В данном ТЗ** | `calculate_hashes("фиксированная строка")` против эталона OpenSSL | реальный `smtplib` к провайдеру; `python -m homework.main` end-to-end |

Следствия:

- Обязательный pytest из задания — **юнит-тест чистой функции**. Он не доказывает, что письмо ушло.
- Успешная доставка письма — **ручной интеграционный сценарий сдачи** (показать входящее). Автоматизировать его в CI без тестового SMTP (например, `aiosmtpd`) дорого относительно ТЗ.
- Тест «`RecordingMailer` получил тело с ФИО и двумя хешами» — узкий интеграционный/компонентный тест **без сети**. Он полезен, но не заменяет эталон OpenSSL для хешей.
- Monkeypatch `smtplib.SMTP` в юнит-тесте хешей — запах: неверный слой.

Рекомендуемая пирамида для домашки:

1. Обязательный юнит-тест `calculate_hashes` на **известной** строке (лучше ASCII без сюрпризов Unicode, плюс отдельно осознать кириллицу ФИО).
2. По желанию: тест канонизации `set` (два «логических» множества равны ⇒ одна строка отчёта).
3. По желанию: тест `Mailer` с Fake.
4. Вне pytest: один живой SMTP-прогон перед сдачей.

### 5.2. pytest и src-layout без обязательного `pip install -e .`

Официальные *Good Integration Practices* pytest:

- рекомендуемый layout: `src/<pkg>` + `tests/` вне пакета;
- src-layout **сильно** рекомендуется, особенно при import mode `prepend`, чтобы тесты не импортировали случайную копию пакета из корня;
- без editable-install локальный пакет **не виден**, пока `src` не добавлен в путь:

  - ad-hoc: `PYTHONPATH=src pytest`
  - постоянно: конфигурационная переменная `pythonpath`

В `pyproject.toml` исторически и наиболее совместимо:

```toml
[tool.pytest.ini_options]
pythonpath = ["src"]
testpaths = ["tests"]
```

Смысл ключей:

- `pythonpath = ["src"]` — аналог `PYTHONPATH=src`: импорт `homework` резолвится в `src/homework`;
- `testpaths = ["tests"]` — не коллекционировать `src/` и `docs/`.

Альтернатива, которую pytest называет предпочтительной для разработки: `pip install -e .` (PEP 660 editable). Тогда тест идёт против того же пакета, что и `python -m homework.main` после установки. Для сдачи полезно **понимать оба** пути: конфиг pytest и editable install.

Дополнительно pytest рекомендует для новых проектов `--import-mode=importlib`, чтобы не мутировать `sys.path` при импорте тестов. Это ортогонально `pythonpath`, но снижает класс ошибок «тест импортировался дважды».

Запуск `python -m homework.main` из корня требует, чтобы пакет был на `sys.path`. Варианты (студент выбирает и документирует в README):

- `PYTHONPATH=src python -m homework.main`
- `pip install -e .` затем `python -m homework.main`
- настройка IDE, эквивалентная PYTHONPATH

src-layout как раз мешает «случайному» импорту из CWD, если пакет лежит только в `src/` — это цель, а не дефект (Ionel Mărieș / PyPA packaging guide: src vs flat).

### 5.3. Независимая верификация эталона MD5 / SHA-256

Требование задания: не считать эталон верным «потому что Python так напечатал». Нужен **другой инструмент**, реализующий те же RFC/FIPS алгоритмы.

#### OpenSSL (`openssl dgst`)

Официальная man-страница `openssl-dgst`: дайджест файла (по умолчанию hex). Примеры:

```bash
openssl dgst -md5 -hex file.txt
openssl dgst -sha256 -hex file.txt
```

или короткие формы `openssl md5`, `openssl sha256`.

Критическая методологическая ловушка: **хешируется ровно та последовательность байтов, что в файле/pipe**, включая перевод строки в конце. `echo 'abc'` на многих оболочках пишет `abc\n`; Python-строка `'abc'` — без `\n`. Эталоны разъедутся.

Надёжный каркас (идея, не готовый тест-код проекта):

1. Зафиксировать **точную** Unicode-строку (желательно сначала ASCII, например `abc`).
2. Подать её в OpenSSL **без добавленного newline**. В POSIX это `printf '%s' 'abc' | openssl dgst -md5`.
3. Аналогично SHA-256.
4. Сверить hex (регистр: и OpenSSL, и `hexdigest()` обычно lowercase).
5. Только затем записать константы в assert.
6. Повторить для строки с кириллицей, убедившись, что терминал/файл в UTF-8: `printf '%s' '...'` в locale UTF-8 или `openssl dgst` по файлу, сохранённому как UTF-8 **без BOM**.

На macOS дополнительно существуют `md5` и `shasum -a 256`; это другие CLI, но те же алгоритмы. Совпадение трёх источников (OpenSSL, BSD `md5`, Python) повышает уверенность.

Проверка «оба хеша от одних байтов»:

- эталон OpenSSL для MD5 и SHA-256 снимается с **одного и того же** pipe/файла;
- в тесте вызывается `calculate_hashes` один раз, оба элемента кортежа сравниваются с двумя эталонами.

Антипрактики:

- скопировать хеш из ChatGPT/LLM без CLI;
- захешировать файл, в котором редактор сохранил `\r\n` или BOM;
- сравнивать MD5 от `'abc'` с SHA-256 от `'abc\n'`.

Рекомендуемая известная строка для первого теста: короткая ASCII. Для неё публично известны дайджесты, и их можно перепроверить в нескольких утилитах. Затем — отдельное осознание, что ФИО в письме хешируется **только как часть полного отчёта**, а не отдельным вызовом.
